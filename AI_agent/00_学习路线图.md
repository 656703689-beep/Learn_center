# AI Agent 开发五级学习路线

> 目标：从完全新手到能独立做项目。业余时间约 4–6 个月。
> 前置要求：Python 基础（会用函数、类、pip、虚拟环境即可）。
> 用法：每完成一项练习或达标一项标准，把 `[ ]` 改成 `[x]`。所有晋级标准打勾后，再进入下一等级。

---

## 等级 1：直连 API——先跟模型"裸聊"（约 1–2 周）

**核心认知：LLM API 是无状态的，每一轮对话都是你把历史拼起来重新发给它。**
这个认知没建立，后面全是空中楼阁。

### 需要掌握
- 基本概念：token、上下文窗口、温度参数、system/user/assistant 三种消息角色
- 不用任何框架，直接用 OpenAI 兼容 SDK 调用（智谱 GLM、DeepSeek、Qwen 都兼容 OpenAI 接口格式）
- 自己维护 `messages` 列表实现多轮对话
- 流式输出（streaming）
- 结构化输出：让模型稳定输出 JSON 并做解析兜底
- 基础工程习惯：超时重试、限流处理、记录每次调用的 token 花费

### 常见错误
- 一上来就学 LangChain 之类的框架，底层 API 不懂，出问题完全不会排查
- 以为模型"记得"上一轮说的话——其实是你没把历史传过去
- Prompt 写得含糊，效果差就怪模型笨，而不是回去改指令
- 不处理超时和限流，程序偶发崩溃还找不到原因
- 调试时反复全量重跑，token 费用失控

### 练习（代码放 `01_API基础/`）
- [ ] 命令行多轮聊天机器人：自己维护对话历史，支持退出时保存
- [ ] 评论分类器：输入商品评论，输出 `{"情感": "...", "类别": "...", "置信度": ...}`，处理 JSON 解析失败
- [ ] 本地文档摘要工具：读 txt/md 文件，输出三句话摘要

### 晋级标准
- [ ] 不查资料能写出完整多轮对话程序，正确维护 messages 列表
- [ ] JSON 输出有解析失败的兜底逻辑（重试或修复）
- [ ] 能向别人讲清楚"API 无状态、上下文是拼出来的"

---

## 等级 2：Tool Use——让模型驱动你的代码（约 2–3 周）

**这一级是 agent 的心脏。所有 agent 框架的核心就是一个循环，你要脱离框架手写一遍。**

### 需要掌握
- Function calling 完整循环：定义工具 schema → 模型决定调用并给参数 → **你的代码执行** → 结果回传 → 模型继续生成
- 工具 schema 设计：描述和参数说明是写给模型看的，不是写给程序员看的
- 失败处理：工具报错时把错误信息回传给模型，让它自己纠正重试
- 多工具场景：模型如何在几个工具间选择

### 常见错误
- 以为模型"执行"了你的代码——模型只输出调用参数，执行永远是你写的代码
- 工具描述照抄开发文档，模型读不懂、用不对
- 工具返回一大坨原始数据塞回上下文，token 爆炸
- 工具一报错程序直接崩，而不是把错误告诉模型让它换个方式
- 一次注册十几个工具，模型选择困难、频繁调错

### 练习（代码放 `02_ToolUse/`）
- [ ] 手写 agent loop：给模型一个 `calculator` 和一个 `get_current_time` 工具，实现完整的"调用→执行→回传→继续"循环（禁止用框架）
- [ ] 天气查询助手（mock 数据也行）：模型自主决定何时查天气、查哪个城市
- [ ] 给等级 1 的聊天机器人加上读写本地文件的工具，做成能记笔记的助手

### 晋级标准
- [ ] 能白板画出 agent loop 全流程
- [ ] 脱离任何框架手写带错误处理的 tool-calling 循环
- [ ] 你设计的工具 schema，模型调用准确率明显高（描述清晰、参数少而明确）

## 等级 3：RAG——让 agent 接入你的知识（约 3–4 周）

### 需要掌握
- Embedding 原理：文本变向量、余弦相似度
- 文档切分策略：固定长度、按结构（标题/段落）、重叠窗口，以及各自的适用场景
- 向量数据库：Chroma 起步最快；本地有 Postgres，可以进阶试 pgvector
- 完整 pipeline：加载 → 切分 → embedding → 入库 → 检索 → 拼 prompt → 生成
- 回答带引用来源；正确处理"知识库中没有答案"的情况
- 进阶：混合检索（关键词 + 向量）

### 常见错误
- Chunk 大小拍脑袋定：太大检索不准，太小丢失上下文
- 只用向量检索，专有名词（产品型号、人名、编号）检索不到——这类词 embedding 分不出区别
- 不给模型"知识库里没有"的逃生口，模型硬编答案（幻觉的常见来源）
- 评估全靠"感觉不错"，没有固定测试题
- 什么问题都想靠微调解决，其实 90% 该调的是检索和切分

### 练习（代码放 `03_RAG/`）
- [ ] 拿自己的真实文档（公司产品资料、技术笔记）建一个本地知识库问答
- [ ] 对比实验：固定 20 个测试问题，对比不同 chunk 大小/重叠下的命中率，用数据说话
- [ ] 加引用功能：回答时标注出自哪个文档哪一段
- [ ] 进阶：混合检索（关键词 + 向量）

### 晋级标准
- [ ] 独立搭完整 RAG pipeline，且能讲清每个环节为什么这样设计
- [ ] 有 20 题的量化测试集，能通过调整切分/检索策略把准确率提上去
- [ ] 系统对知识库没有的问题能正确拒答，而不是编造

## 等级 4：多步 Agent——自主规划、记忆与纠错（约 1–2 月）

### 需要掌握
- ReAct 模式：推理与行动交替，"想一想→做一步→看结果→再想"
- 主流框架选一个深入（LangGraph 或 OpenAI Agents SDK 都可以）——**但带着等级 2 的底层理解去学**，知道框架每一步替你做了什么
- 图编排：条件分支、循环、人工介入节点（human-in-the-loop）
- 记忆系统：短期（上下文内压缩）+ 长期（持久化存储）
- 护栏：最大步数上限、预算上限——agent 会失控，必须设闸
- MCP 协议概念：把工具做成标准化服务供 agent 调用
- 给非确定性系统建回归测试集

### 常见错误
- 单 agent 还没跑稳就搭多 agent 系统——90% 的场景一个 agent + 好工具就够了
- 不设步数/预算上限，agent 死循环烧钱
- 上下文无限增长直到爆窗口，长任务后期质量骤降
- 框架当黑盒用，出问题不知道是框架的锅还是自己的锅
- 改了 prompt 没有评估集对比，不知道是变好还是变坏
- 过度工程：为了"看起来像 agent"堆不必要的复杂度

### 练习（代码放 `04_多步Agent/`）
- [ ] 研究助手：给定主题，agent 自主搜索 → 阅读 → 汇总成报告，带步数上限和过程日志
- [ ] 给等级 3 的 RAG 助手加多轮记忆和历史压缩
- [ ] 用 LangGraph 画一个带人工确认的流程：Agent 生成 SQL → 人工审核 → 执行 → 汇报结果
- [ ] 给自己的 agent 建 10 个 case 的回归测试集，每次改动跑一遍

### 晋级标准
- [ ] 能用框架实现带循环、分支、人工介入的多步 agent，并说清框架在每一步做了什么
- [ ] 有成本和步数护栏，任务再复杂也不会失控
- [ ] 有可重复跑分的评估集，每次改动有数据对比
- [ ] 能判断一个需求该用固定流程（workflow）还是自主决策（agent）——这是架构判断力的分水岭

## 等级 5：完整交付——从 demo 到产品（约 1–2 月）

### 需要掌握
- 产品化：FastAPI 做后端服务，Gradio/Streamlit 快速搭界面（或正经前端）
- 可观测性：日志 + tracing，每次 LLM 调用、工具调用可回放（Langfuse 等）
- 安全：prompt injection 防御（用户一句"忽略之前指令"不该劫持你的 agent）、工具权限最小化
- 评估体系：离线评估集 + LLM-as-judge + 真实用户反馈
- 成本与延迟优化：模型分级（简单任务用小模型）、结果缓存
- 迭代方法论：最小版本先上线，用真实反馈驱动改进

### 常见错误
- 憋着追求完美不敢发布——agent 产品必须靠真实使用反馈才能变好
- 上线没监控，出问题两眼一抹黑，连用户问了什么都还原不出来
- 无视注入攻击：知识库文档里藏一句恶意指令都可能劫持 agent
- 全链路用最贵的模型，成本撑不住也不敢换，因为没做过分级测试
- 作品集里只有"演示级"项目，讲不出量化效果和失败案例

### 练习（毕业项目，代码放 `05_毕业项目/`，选一个真实场景完整交付）
- [ ] 能耗/生产数据问答助手：自然语言查数据库（Text-to-SQL）+ 自动生成分析报告（可复用 pandas 和业务经验）
- [ ] 或：企业知识库客服：RAG + 多轮对话 + 搞不定时人工升级
- [ ] 硬性要求：有界面、有 tracing 日志、有 20+ case 评估集、有安全护栏、README 讲清架构和量化效果

### 毕业标准（"能独立做项目"的定义）
- [ ] 从需求分析到部署上线全流程独立完成，技术选型说得出理由
- [ ] 出问题能靠 tracing 快速定位到是 prompt、检索还是工具层的锅
- [ ] 能向别人讲清系统的能力边界和失败模式（知道它什么时候不行，比知道它行什么更重要）
- [ ] 有至少 1 个真实部署（内网或个人服务器都算）的完整项目

---

## 路线设计说明

- 等级 1–2 刻意不用框架：是为了让你以后用框架时不被它绑架
- 等级 4 才引入框架：那时你已经知道框架在替你做什么
- 每一级的晋级标准都是"能做到什么"，不是"看过什么"
